# 02 · Giving the model hands

The model can't run code or reach the internet. So how does any "AI agent" book a flight or
query a database? It doesn't, directly. It asks *your* code to do it. That request-and-respond
handshake is called tool use, and it's the single mechanism every agent is built on. Get this
lesson and the rest of the course is variations on it.

By the end you'll watch the model ask for a calculator, run it yourself, hand back the answer,
and see the model finish the job.

## The one idea

You hand the model a list of tools it's allowed to ask for. When it wants one, it doesn't run
anything — it returns a structured request: "please call `calculator` with
`{expression: '23*47'}`." Your code runs that, sends the result back, and the model writes its
final answer using it.

Four steps, every time:

1. You send the conversation plus a list of tool definitions.
2. The model replies with `stop_reason == "tool_use"` and a block naming the tool and its input.
3. Your code runs the tool and sends back a `tool_result`.
4. The model uses the result to write its answer.

## Reading the code

A tool definition is just a schema. Think of it as the API docs the model reads to decide
whether and how to call something. The `description` matters more than it looks — it's how the
model knows what the tool is for.

```python
TOOLS = [
    {
        "name": "calculator",
        "description": "Evaluate a basic arithmetic expression and return the number.",
        "input_schema": {
            "type": "object",
            "properties": {
                "expression": {
                    "type": "string",
                    "description": "An arithmetic expression, e.g. '23 * 47 + 1'.",
                }
            },
            "required": ["expression"],
        },
    }
]
```

The actual tool is plain Python. The model never sees this function; it only sees the schema
above. You're the one who connects the name `"calculator"` to real code.

```python
def calculator(expression: str):
    # eval is fine for a toy lesson; lesson 09 covers why you'd sandbox this in prod.
    return eval(expression, {"__builtins__": {}}, {})
```

Now the handshake. We send a question and the tools. The model comes back wanting the
calculator — `stop_reason` is `"tool_use"`, and we pull out the block to see exactly what it
asked for.

```python
resp = client.messages.create(model=MODEL, max_tokens=400, tools=TOOLS, messages=messages)
print("stop_reason:", resp.stop_reason)  # -> 'tool_use'

tool_use = next(b for b in resp.content if b.type == "tool_use")
print(f"MODEL WANTS TO CALL: {tool_use.name}({tool_use.input})")
```

We run it ourselves, then feed the answer back. This is the step people miss: you append the
model's request *and* your result to the conversation, then call the model again so it can
finish.

```python
result = calculator(**tool_use.input)

messages.append({"role": "assistant", "content": resp.content})
messages.append({
    "role": "user",
    "content": [{"type": "tool_result", "tool_use_id": tool_use.id, "content": str(result)}],
})
final = client.messages.create(model=MODEL, max_tokens=400, tools=TOOLS, messages=messages)
print("\nMODEL FINAL:", final.content[0].text)
```

The `tool_use_id` is how the model matches your result to the request it made. With one tool
it seems like overkill; with several in flight it's how nothing gets crossed.

## What to watch for

- Your code always runs the tool. The model only ever *asks*. If something dangerous happens,
  it's because your code did it — which is also why you get to refuse (lesson 09).
- The model has no internet and no compute until you give it a tool. A model with no tools is
  back to being autocomplete.
- This lesson handles exactly one tool call. If a task needed the calculator twice, this code
  would miss the second request. That gap is the whole reason for lesson 03.

## Recap

- Tools are schemas you offer; the model requests them, your code runs them.
- The loop is: send tools, get a request, run it, send the result, get the answer.
- `tool_use_id` ties each result to its request.
- Good tool descriptions are good API docs — the model reads them to choose.
